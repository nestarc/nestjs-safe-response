# v0.15.0 Design Spec: Contract & DX Hardening

**Date:** 2026-06-13
**Version:** 0.15.0
**Theme:** Contract stability, error catalog DX, OpenAPI fidelity, and runtime hardening before v1.0.0

## Overview

v0.14.0 added four major user-facing capabilities: field selection, error catalog, API version metadata, and `StreamableFile` auto-detection. v0.15.0 should not add another large subsystem. Instead, it should close the remaining contract and DX gaps around those features so the library is safer to use in production and closer to a v1.0.0 API freeze.

All changes in this release are additive or defensive. Existing public APIs remain valid. Where naming is ambiguous, v0.15.0 adds clearer aliases while keeping old option names as compatible aliases.

## Goals

1. Make the error catalog useful across runtime throws and Swagger documentation.
2. Keep generated OpenAPI schemas aligned with runtime DTOs and client types.
3. Harden field selection and numeric metadata against invalid or hostile inputs.
4. Improve composite decorator coverage for the features added after v0.13.0.
5. Add verification that catches contract drift before v1.0.0.

## Non-goals

The following are intentionally deferred:

- OpenTelemetry direct integration. Existing CLS integration remains the supported path for trace/correlation metadata in v0.15.0.
- Runtime cache hint metadata. This needs a separate API design because it overlaps with gateways, CDN headers, and NestJS cache interceptors.
- Runtime `nestjs-paginate` integration. v0.15.0 does not add an adapter dependency or ORM-specific runtime behavior. Documentation recipes can be added only if they are part of the README/docs sweep.
- Breaking removal of public metadata constants. v0.15.0 can document the planned cleanup, but removal belongs to v1.0.0 or later.

## 1. Error Catalog DX Completion

### Problem

`defineErrors()` and `SafeException` centralize runtime error definitions, but the public API is not complete:

- `SafeException` accepts any `string`, so catalog keys are not type-safe at throw sites.
- `@ApiSafeErrorResponse()` and `@ApiSafeErrorResponses()` still document errors by numeric status/config only.
- Users must duplicate catalog status, message, details, and description when writing Swagger decorators.

### Solution

Add catalog-aware helpers that preserve literal key types and avoid duplicating error metadata.

### Public API

```typescript
const errors = defineErrors({
  USER_NOT_FOUND: {
    status: 404,
    message: 'User not found',
    description: 'The requested user does not exist',
  },
  EMAIL_TAKEN: {
    status: 409,
    message: 'Email already registered',
  },
});

const AppSafeException = createSafeException(errors);

throw new AppSafeException('USER_NOT_FOUND');

@ApiSafeCatalogError(errors, 'USER_NOT_FOUND')
@ApiSafeCatalogErrors(errors, ['USER_NOT_FOUND', 'EMAIL_TAKEN'])
```

### API Shape

```typescript
export function createSafeException<K extends string>(
  catalog: ErrorCatalog<K>,
): new (
  key: K,
  options?: { message?: string; details?: unknown },
) => SafeException;

export function ApiSafeCatalogError<K extends string>(
  catalog: ErrorCatalog<K>,
  key: K,
  options?: Omit<ApiSafeErrorResponseOptions, 'code' | 'message' | 'details'> & {
    code?: string;
    message?: string;
    details?: unknown;
  },
): MethodDecorator;

export function ApiSafeCatalogErrors<K extends string>(
  catalog: ErrorCatalog<K>,
  keys: readonly K[],
): MethodDecorator;
```

`ApiSafeCatalogError()` resolves defaults from the catalog:

- `status` from `catalog[key].status`
- `code` defaults to the catalog key
- `message` defaults to `catalog[key].message`
- `details` defaults to `catalog[key].details`
- `description` defaults to `catalog[key].description` or `Error response (${status})`

### Compatibility

`SafeException` remains unchanged and still accepts `string`. The typed factory is the recommended path for applications that want compile-time key safety.

## 2. OpenAPI Contract Alignment

### Problem

DTOs and runtime responses now expose richer metadata, but fallback schema generation in `applyGlobalErrors()` can drift from the DTO definitions. In particular, fallback error schemas must stay aligned with `ErrorResponseMetaDto` and `ProblemDetailsDto`, including `meta.apiVersion` and extensible context metadata.

Composite decorators also have runtime E2E coverage, but Swagger E2E coverage is thinner than the individual decorators they compose.

### Solution

Keep fallback schemas in `src/swagger/global-errors.ts` synchronized with DTOs and expand Swagger E2E coverage for composite and cursor decorators.

### Requirements

- Fallback standard error schema includes `meta` with:
  - `responseTime`
  - `deprecation`
  - `rateLimit`
  - `apiVersion`
  - `additionalProperties: true`
- Fallback Problem Details schema includes `meta.apiVersion`.
- `applyGlobalErrors()` keeps route-level responses higher priority than global responses.
- Swagger E2E includes routes for:
  - `@SafeEndpoint`
  - `@SafePaginatedEndpoint`
  - `@SafeCursorPaginatedEndpoint`
  - `@ApiCursorPaginatedSafeResponse`
  - catalog-aware error decorators

### Files Modified

| File | Change |
|------|--------|
| `src/swagger/global-errors.ts` | Align fallback schemas with current DTO metadata |
| `src/swagger/global-errors.spec.ts` | Add fallback schema regression tests |
| `test/e2e/swagger-test.controller.ts` | Add composite, cursor, and catalog decorator routes |
| `test/e2e/swagger-schema.e2e-spec.ts` | Assert schemas and update snapshots |
| `test/e2e/__snapshots__/swagger-schema.e2e-spec.ts.snap` | Snapshot updates |

### Tests

- Unit tests verify fallback schemas include current metadata fields.
- E2E OpenAPI parser validation still passes.
- Snapshots fail if composite/cursor/catalog response schemas drift.

## 3. Field Selection Hardening and Composite Support

### Problem

Field selection is now a headline feature. The current implementation covers normal inputs, but it should be hardened before v1.0.0:

- Field lookup uses `key in obj`, which can match inherited properties.
- Nested output writes arbitrary keys, including prototype-sensitive names.
- There is no cap on field count or path length.
- Composite decorators do not expose `fieldSelection`, so users must stack `@FieldSelection()` manually even when using `@SafeEndpoint()`.

### Solution

Harden parsing and object traversal, then expose field selection through all composite endpoint decorators.

### Public API

```typescript
export interface FieldSelectionOptions {
  queryParam?: string;
  separator?: string;
  maxDepth?: number;
  maxFields?: number;
  maxFieldLength?: number;
}

export interface SafeEndpointOptions {
  fieldSelection?: boolean | FieldSelectionOptions;
}

export interface SafePaginatedEndpointOptions {
  fieldSelection?: boolean | FieldSelectionOptions;
}

export interface SafeCursorPaginatedEndpointOptions {
  fieldSelection?: boolean | FieldSelectionOptions;
}
```

### Runtime Rules

- Only own enumerable properties are selectable.
- Reserved path segments are ignored:
  - `__proto__`
  - `prototype`
  - `constructor`
- Empty field names are ignored.
- Fields deeper than `maxDepth` are ignored.
- If `maxFields` is set, parsed fields are capped to that count.
- If `maxFieldLength` is set, individual field paths longer than the limit are ignored.
- Arrays keep existing behavior: top-level arrays apply selection to each item.
- Nested arrays are not expanded in v0.15.0; this limitation is documented.

### Precedence

Field selection precedence remains:

1. Route decorator or composite option
2. Module option
3. Disabled

`fieldSelection: false` on a composite decorator explicitly disables module-level field selection for that route.

### Tests

- Inherited properties are not selected.
- Field count and field length limits are enforced.
- Composite `fieldSelection: true` enables partial response.
- Composite `fieldSelection: false` disables module-level field selection.

## 4. Runtime Metadata Hardening

### Problem

Several metadata paths accept invalid numeric values:

- Pagination shape checks accept any JavaScript `number`, including `NaN`, `Infinity`, negative values, and fractional values.
- Rate limit parsing rejects `NaN` but not `Infinity` or invalid negative values.
- The exception filter replies even if the underlying platform response has already been sent.

These cases can produce invalid JSON metadata or double-send failures under unusual runtime conditions.

### Solution

Introduce small platform-neutral validation helpers and already-sent response checks.

### Numeric Rules

Offset pagination:

- `total`, `page`, and `limit` must be finite numbers.
- `page` and `limit` must be positive integers.
- `total` must be a non-negative integer.
- Invalid values make `isPaginatedResult()` return `false`, preserving existing shape-mismatch warning behavior.

Cursor pagination:

- `limit` must be a positive finite integer.
- `totalCount`, when present, must be a non-negative finite integer.
- Invalid values make `isCursorPaginatedResult()` return `false`.

Rate limit metadata:

- `limit`, `remaining`, and `reset` must be finite numbers.
- `limit` and `reset` must be non-negative.
- `remaining` must be non-negative.
- `retryAfter`, when present, must be finite and non-negative.
- Partial or invalid data suppresses `meta.rateLimit`.

### Already-sent Response Handling

Extend `SafeHttpResponse` with optional platform flags:

```typescript
export interface SafeHttpResponse {
  headersSent?: boolean;
  writableEnded?: boolean;
  sent?: boolean;
}
```

Add helper:

```typescript
export function isResponseSent(response: SafeHttpResponse): boolean;
```

The exception filter checks this before setting headers or calling `httpAdapter.reply()`. If the response is already sent, it logs the exception with request context and returns without attempting another write.

- Invalid rate limit headers suppress `meta.rateLimit`.
- Already-sent Express response does not call `reply()`.
- Already-sent Fastify response does not call `reply()`.
- 5xx logging remains intact.

## 5. Problem Details Documentation Naming

### Problem

Composite decorator options use `problemDetails?: boolean`, but this option only affects Swagger documentation. Runtime Problem Details mode is controlled by `SafeResponseModule.register({ problemDetails: true })`. The shared name is easy to misread.

### Solution

Add a clearer alias while preserving the existing option:

```typescript
export interface SafeEndpointOptions {
  errorFormat?: 'safe' | 'problem';
  problemDetails?: boolean;
}
```

Rules:

- `errorFormat: 'problem'` means composite error Swagger decorators use `ApiSafeProblemResponse()`.
- `errorFormat: 'safe'` means composite error Swagger decorators use `ApiSafeErrorResponse()`.
- `problemDetails: true` remains supported as an alias for `errorFormat: 'problem'`.
- If both are present, `errorFormat` takes priority.

### Files Modified

| File | Change |
|------|--------|
| `src/interfaces/index.ts` | Add `errorFormat` to composite option interfaces |
| `src/decorators/index.ts` | Resolve error documentation format from `errorFormat ?? problemDetails` |
| `src/decorators/decorators.spec.ts` | Add precedence tests |
| `README.md`, `README.ko.md` | Clarify runtime vs Swagger-only behavior |

## 6. Client and Type Contract Verification

### Problem

Server and client response types are intentionally duplicated because the client subpath has zero NestJS runtime dependencies. v0.14.0 already exposed how easy it is for these contracts to drift.

### Solution

Keep the duplication for now, but make the verification stronger.

### Requirements

- Add runtime tests for `hasFieldSelection()`:
  - valid non-empty string array returns true
  - empty array returns false
  - missing `fields` returns false
  - non-array values return false
  - mixed non-string arrays return false
- Add `tsd` negative tests for invalid `apiVersion` and `fields` types.
- Generated-client verification is limited to existing tooling in v0.15.0. Do not add a new OpenAPI generator dependency in this release. If existing dependencies are not enough, document the generated-client smoke test as a pre-v1.0.0 verification task instead.

### Files Modified

| File | Change |
|------|--------|
| `src/client/client.spec.ts` | Add `hasFieldSelection()` runtime guard tests |
| `index.test-d.ts` | Add stronger metadata type regression assertions |
| `docs/reports/2026-06-13-v0.15.0-verification-report.md` | Add release verification checklist when implementation is complete |

## Release Acceptance Criteria

v0.15.0 is complete when:

- `npm run build` passes.
- `npm run lint` passes.
- `npm test` passes.
- `npm run test:e2e` passes.
- `npm run test:types` passes.
- Swagger snapshots are updated intentionally and parser validation passes.
- README and README.ko document all new public APIs and option aliases.
- CHANGELOG includes a 0.15.0 section with Added/Changed/Fixed entries.
- `npm pack --dry-run` confirms the expected package contents.

## Recommended Implementation Order

1. Field selection hardening and composite support.
2. Runtime numeric and response-sent hardening.
3. Error catalog typed factory and Swagger helpers.
4. OpenAPI fallback schema alignment and Swagger E2E expansion.
5. Problem Details docs alias.
6. Client/type verification and documentation updates.

This order starts with defensive changes that reduce risk in existing v0.14 behavior, then adds new helper APIs, then updates documentation and release verification.

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Catalog helper API becomes too broad | Keep helpers small and catalog-object based; do not introduce global mutable catalog state |
| Field selection hardening changes edge behavior | Only ignore unsafe/invalid fields; valid existing field paths keep current behavior |
| Numeric validation suppresses metadata users previously saw | Treat invalid numeric metadata as a shape mismatch and emit existing warnings |
| `problemDetails` option alias creates confusion | Prefer `errorFormat` in docs and mark `problemDetails` as a compatibility alias |
| Generated-client smoke test needs a new dependency | Do not add the dependency in v0.15.0; document the smoke test as a pre-v1.0.0 verification task |

## Out-of-scope Backlog After v0.15.0

- OpenTelemetry direct metadata resolver.
- Cache hint metadata and decorators.
- `nestjs-paginate` recipe or adapter package.
- Shared source generation for server/client response contracts.
- v1.0.0 public export cleanup for metadata constants.
